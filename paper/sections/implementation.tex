\section{Implementation}
\label{sec:implementation}

\subsection{Two engines, one verdict}

The system has two runtime endpoints with opposite profiles.
Server-side calls (registry publish, the \texttt{/check} route, the
validation pipeline) run on Django and use Python detectors in
\texttt{apps/api/scanners/}. Agent-side calls (the MCP gate, the
\texttt{phub} CLI) run on Node and use TypeScript detectors in
\texttt{packages/phub/src/scanners/}. Keeping one canonical engine and a
thin port at the other end invites drift the moment a contributor edits
one and forgets the other, a known failure mode for security-critical
code.

We treat cross-language parity as a CI-enforced contract rather than a
code-review claim~\cite{primitivehub:2026:adr-0023}. For any sample $s$
and detector $d$, the verdict severity and the boolean passed flag must
be identical across engines, and the per-detector
\texttt{(tp, fp, tn, fn)} tuples measured against the shared corpus must
agree byte-for-byte. As Section~\ref{sec:evaluation} shows, that
contract holds on every in-sample sample; the held-out slice, which the
gate does not police, is where the two engines still diverge. The cost
of two engines is real (every detector change is two edits and a
re-check), and so is the benefit: the byte-identical property is what
lets the agent-side gate carry the same guarantee as the server-side
pipeline.

\subsection{The markdown-context analyzer}

Most detectors share an analyzer that identifies three syntactic regions
of a document: YAML frontmatter, fenced code blocks (per
CommonMark~\cite{CommonMark:2024:spec}), and inline code spans. It walks
the document once and yields offset lists, so per-detector lookups are
constant time. Introducing it closed three precision-defense ledger
entries at once: detectors stopped firing on documented teaching
examples, on inline-code mentions of vendor commands, and on frontmatter
that names attack-shape keywords. Syntactic attack carriers (a fenced
\texttt{system} marker, a hidden \texttt{<!-- instructions -->} comment)
stay unprotected, so they still fire on their intended shape.

A second pass classifies the prose \emph{around} a
match~\cite{primitivehub:2026:adr-0036} as negation (``never run
\texttt{curl|sh}''), mention (``Stripe's typography''), or declaration
(``CC-BY-4.0''), plus a quoted-trigger predicate for a phrase wrapped in
paired quotes. This is what lets a detector distinguish defender prose
that enumerates an attacker phrase from attacker prose that uses it.

\subsection{The corpus as a regression gate}

The corpus is not only a test set; it is the contract each pull request
passes through. The most recent committed baseline under
\texttt{bench/baseline/} is the floor. Per detector, a pull request may
not drop F\textsubscript{1} by more than 0.02 against the floor on
either engine without an explicit, declared recall trade. A single
script, \texttt{bench/scripts/gate.sh}, discovers the latest baseline
per language, runs both measurement scripts, and runs the parity check.
It exits zero only if no in-sample F\textsubscript{1} regression exceeds
tolerance \emph{and} cross-language tuple parity holds. A companion step
re-renders the public scoreboard and fails the build if
\texttt{docs/evaluation.md} would go stale, so the published numbers
cannot quietly drift from the measured ones.

When the gate fires, the author has three principled options: close the
regression with a lockstep detector change in both engines, relabel the
offending sample with a numbered ledger entry, or declare a recall
trade in the pull request. Silent acceptance is not one of them.

\subsection{Paired ledgers}

The discipline that prevents tuning past the optimum is a pair of
append-only, numbered ledgers borrowed from AV
practice~\cite{Christodorescu:2003:static-malware}. Every
diagnosed finding is classified into exactly one of four paths before a
change ships:

\begin{description}
  \item[Path A] edit the primitive's prose, when the finding is a real
    precision hazard caused by careless drafting.
  \item[Path B] add a narrow allow entry in policy, which is rejected at
    review unless it ships with a matching ledger entry naming its
    scope.
  \item[Path C] ratchet the detector in lockstep across both engines,
    with a corpus sample that locks the fix and a recorded
    F\textsubscript{1} delta.
  \item[Path D] escalate an ambiguous finding to a security reviewer;
    never allow it silently.
\end{description}

As of this submission the false-positive ledger holds 14 entries
(FP-001 through FP-014) and the false-negative ledger holds 25 (FN-001
through FN-025). Each names the corpus sample, classifies the path,
records the resolution, and, after closure, logs the F\textsubscript{1}
delta and the version bump. Together the two ledgers are the audit trail
a reviewer walks to check any claim in Section~\ref{sec:evaluation}.

\subsection{Reproducing the numbers}

The corpus is CC-BY-4.0; the detectors and tooling are Apache-2.0. A
reviewer reproduces every number in Section~\ref{sec:evaluation} from a
clean clone:

\begin{lstlisting}[language=bash]
git clone https://github.com/DevXYZx/primitivehub.git
cd primitivehub
pnpm install --frozen-lockfile
pnpm --filter @primitivehub/phub build
(cd apps/api && uv sync --all-extras)
bench/scripts/gate.sh            # per-detector P/R/F1, both engines
python bench/scripts/render-evaluation.py --check
python bench/cli/replay.py --sample S-001
\end{lstlisting}

The gate prints per-detector precision, recall, and F\textsubscript{1}
for both engines and exits zero only if the regression contract holds.
The replay tool re-runs any single sample through the detectors and
prints its per-detector outcome (TP, FN, FP, or TN), so a reviewer can
ask ``show me this specific finding'' independently of the gate's
blocking semantics.
