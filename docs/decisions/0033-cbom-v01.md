# ADR-0033: CBOM v0.1 — Context Bill of Materials wire format + `phub cbom` subcommand

**Status:** Accepted
**Date:** 2026-06-04
**Related:** ADR-0011 (Sigstore backend abstraction), ADR-0021 (Trust
Contract conformance pattern), ADR-0023 (phub CLI + detector parity
rule), ADR-0025 (Active posture + `phub audit`), ADR-0026 (`phub.lock`
format + drift detection), ADR-0028 (`phub install`), ADR-0032
(Scanner conformance suite), `docs/cbom-v0.1.md`,
`docs/execution-plan.md` § "Trust Runtime architecture".

## Context

The PrimitiveHub Trust Runtime — as named in `docs/execution-plan.md`
and `docs/doctrine.md` — has three pillars:

1. **Trust Contract** (verification wire format) — shipped PR 4.x, spec
   `docs/trust-contract-v0.1.md`.
2. **Context CI Top 10** (threat taxonomy + detector roster) — shipped
   PR 5.6.3 (10/10 detectors), spec `docs/context-ci-top-10-v0.1.md`.
3. **CBOM — Context Bill of Materials** (enumeration / inventory) —
   **this ADR**.

Two of the three pillars exist as versioned public specs with
conformance suites and ratchet discipline. The third pillar — CBOM —
has been informally implied by `phub audit` JSON output and the
`phub.lock` artifact list, but has never been spec'd as its own
artifact with its own wire format, conformance criterion, and consumer
contract.

This is a load-bearing gap. The paper's claim is that AI-agent
context is a new supply-chain layer; the enterprise reviewer's first
question is *"give me the SBOM-equivalent for context"*. Without a
named CBOM artifact, the answer is "run `phub audit --json` and parse
the artifact list" — which is correct but inscrutable. SBOMs got
adopted because they were a single, vendor-neutral, schema-versioned
artifact, not because anyone loved JSON parsing.

The remedy is the same shape as ADR-0026 (lock) and ADR-0021 (Trust
Contract): a canonical wire format, a versioned spec doc, a
conformance suite, and a CLI surface (`phub cbom`).

## Decision

### 1. Adopt `docs/cbom-v0.1.md` as the canonical wire-format spec

The spec defines:

- Top-level JSON shape (`cbomFormat`, `cbomVersion`, `tool`, `subject`,
  `topTen`, `components`, `summary`).
- The component object schema (`path`, `classification`,
  `contentDigest`, `sizeBytes`, `attestation`; optional `displayName`,
  `primitiveVersion`).
- The closed classification vocabulary, deliberately identical to the
  audit / lock vocabulary (`agents-md`, `claude-md`, …, `mcp-config`).
- Canonical-JSON rules — alphabetic key sort, 2-space indent, trailing
  newline, UTF-8 — identical to the `phub.lock` rules.
- Reproducibility: byte-identical re-stamps on unchanged workspaces.
- Explicit deferrals (dependency graph, CBOM signing, SPDX/CycloneDX
  exporters, scanner verdict inclusion).

### 2. Implement `phub cbom [<path>]` as the reference producer

CLI shape mirrors `phub audit`:

```
phub cbom [<path>]
  --output <file>       Write CBOM JSON to <file> instead of stdout.
  --max-files <N>       Walker cap (default 5000, same as audit).
  --max-depth <N>       Depth cap (default 12, same as audit).
  --lock-path <path>    Override the auto-discovered phub.lock for
                        attestation cross-referencing.
```

Exit codes:

- `0` — CBOM generated successfully.
- `2` — usage error, unreadable path, invalid lock under the
  attestation cross-reference.

The implementation reuses `runAudit()` internally (without the
scanner / policy / SARIF paths). This keeps the discovery + digest +
classification logic single-sourced — there is exactly one
classifier, exactly one walker, exactly one digest implementation
across `phub audit`, `phub watch`, `phub install`, and `phub cbom`.

### 3. CBOM v0.1 is TS-only; Python parity is v0.2

ADR-0023's detector-parity rule applies to **detection logic**
(regex patterns / classification thresholds). The CBOM producer is an
**orchestration surface** over the existing classifier + digest
kernel — same category as `phub audit`, `phub watch`, `phub install`.
None of those have a Python equivalent today; the parity rule does
not extend to them.

A future Python `phub_py cbom` (v0.2 candidate) will be required to
pass the same conformance fixtures introduced by this ADR.

### 4. Conformance suite (parallel to ADR-0021 / ADR-0032)

Layout under `docs/cbom/conformance/`:

```
docs/cbom/conformance/
├── manifest.json                       # fixture → expected-CBOM mapping
└── fixtures/
    └── minimal-workspace/
        ├── input/
        │   ├── AGENTS.md
        │   ├── CLAUDE.md
        │   └── apps/web/content/primitives/example.md
        └── expected.cbom.json
```

The TS conformance test (`packages/phub/test/cbom-conformance.test.ts`)
walks each fixture's `input/` directory through the producer and
compares stdout to `expected.cbom.json` byte-for-byte. Re-running
against the same `input/` MUST produce identical output (the
reproducibility property is part of the suite, not a separate
assertion).

### 5. Relationship to `phub.lock`

The CBOM and lock are siblings, not duplicates. ADR-0026 § 3 defined
the lock as a **drift detector** — its job is to make surprise
changes in CI loud. The CBOM is an **inventory artifact** — its job
is to publish a stable, vendor-neutral component list to downstream
consumers. Same source-of-truth (the classifier + digest), different
output shape:

- Lock: `(path, classification, digest, attestation)` per artifact.
- CBOM: `(path, classification, digest, sizeBytes, attestation,
  [displayName, primitiveVersion])` per artifact + workspace summary.

When both are present, the CBOM **reads the lock for attestation
state** so the two artifacts agree on provenance. When no lock
exists, all components are `unattested`.

This is the same composition principle as ADR-0026 itself: surfaces
share the lower-level kernel, but each one packages a different
external contract.

### 6. Explicit deferrals (v0.1 → v0.2 ratchets)

The CBOM v0.1 producer does NOT ship:

| Deferral | Why deferred | Target |
|----------|--------------|--------|
| Dependency graph (`(consumer, dependency)` edges between primitives) | Requires defining what "imports" means for markdown — `[[wiki-links]]`, explicit `related:` frontmatter, etc. Out of scope for the inventory contract; needs its own ADR. | v0.2 |
| Signing the CBOM itself (in-toto Statement, Sigstore-signed) | Requires the Sigstore backend ([ADR-0011](./0011-sigstore-backend-abstraction.md)) to be wired into the CLI, which is a PR 4.x scope item. | v0.2 |
| ~~SPDX 2.3 / CycloneDX 1.5 exporters~~ | ~~Both are useful for enterprise SBOM pipelines, but writing them before the native format is locked invites premature compromise.~~ Shipped in PR 5.11 — the native CBOM landed first (PR 5.9), giving us a stable internal model to project from. Both exporters preserve the byte-identical re-stamp property via SHA-256-derived URNs and epoch-zero timestamps. See `docs/cbom-v0.1.md` § 7.1. | ✓ |
| Scanner verdict inclusion | Keeps the v0.1 wire format minimal. `phub audit --json` and `phub cbom --json` remain separate calls in v0.1; a v0.2 composition surface (`phub cbom --include-verdicts`) is reserved. | v0.2 |
| Cross-workspace deduplication | Useful only for multi-project audits; pre-launch we have one workspace. | v0.3 |

## Consequences

**Positive:**

- The Trust Runtime architecture diagram closes — all three named
  pillars (Trust Contract, Top 10, CBOM) now have versioned public
  specs with conformance suites and ratchet discipline.
- Enterprise reviewers asking *"give me the SBOM for context"* get a
  single artifact with a stable URL (`https://primitivehub.ai/cbom/v0.1.json`)
  rather than instructions to parse audit JSON.
- The paper can cite `docs/cbom-v0.1.md` § 2 + § 3 directly when
  defining the inventory layer of the Trust Runtime, rather than
  hand-waving.
- The reference implementation (`phub cbom`) is also the consumer's
  v0.1 verifier (`phub cbom --verify <path>` reserved for v0.2). One
  binary, one schema, one conformance suite.

**Negative:**

- Two artifacts (lock + CBOM) over the same source-of-truth requires
  consumers to understand both. We accept this — the lock is for CI
  drift, the CBOM is for inventory publishing, and conflating them
  would weaken both contracts.
- A v0.2 ratchet will be required when the dependency graph or the
  signed-CBOM wrapper lands. The spec's § 10 explicitly reserves the
  bump and lists the deferred features, so the ratchet has no
  surprises.

## Alternatives considered

**Use SPDX 2.3 as the native format.** SPDX models compiled-code
components (packages with versions, licenses, supplier metadata).
Mapping `AGENTS.md` to SPDX's `Package` / `File` taxonomy requires
lossy translation: an agent-context artifact is not a versioned
package, has no supplier, has no license in the SPDX sense.
Native-CBOM-first + optional SPDX-exporter-later (per § 6) preserves
fidelity without locking us into a translation table.

**Reuse `phub.lock` as the inventory artifact.** The lock's purpose is
drift detection in CI — it does NOT carry sizes, display names, or
the topTen pointer that an inventory artifact needs. Stretching the
lock to carry both would force CI to re-stamp + diff on changes that
don't affect drift (size shifts, frontmatter edits), poisoning the
drift signal. Two artifacts, two contracts, one kernel.

**Ship CBOM as a flag on `phub audit`.** `phub audit --cbom` was
considered. Rejected: `phub audit` is the active-posture surface (it
runs the scanner roster and exits 1 on findings); coupling the CBOM
producer to that flow means CBOM output is gated by scanner state.
The CBOM is an inventory, not a verdict; it should be producible from
a workspace with known-failing scanner state. Separate subcommand.
